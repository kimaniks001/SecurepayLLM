# UI Completion — Phase 8: Agreement Money Authority, Funding, Payment Ready, Release & Settlement Truth

Branch `feat/ui-phase8-money` from UI `main` @ `304c7808f26b263067fc3076c46f757056fc64c6` (Phase 7 / PR #33 merged). SecurePayAPI `main` @ `75a490bc7bdbe0b213dad00037d7f72be579c13b` (read-only, **not modified**; the API was **not run**). Not merged, not deployed.

## Decision in one paragraph
SecurePay's participant financial commands cannot be proven **environment-safe** (`FinancialParticipantCommandEnvironmentGuard` allows local/test/sandbox only, and **no read exposes that capability**) nor **atomic against a concurrent Agreement version change** (no command carries or compares an expected version). Exactly as Phase 6 Apply and Phase 7 Start/Review/Complete, every financial *command* is therefore **withheld**; the whole **read** journey is kept and made honest. Environment is never inferred from hostname, `import.meta.env`, rail or URL.

## What changed
- **Convergence.** Agreement Detail → Money is now a compact doorway ("Open Money"); the old `MoneyWorkspace` is no longer used by the workspace. The handoff is **in memory** (`handoff.ts`): `#/money` stays the one route, no agreement/obligation/intent ids in URL/storage/history. Money opens on the chosen Agreement with context ("Bathroom retiling · version 1"). Direct or refreshed `#/money` opens Money Home.
- **Idempotency.** All Money gateways take **caller-supplied** keys (no gateway mints a fresh key per call). 
- **Exact amounts.** `parseMinorUnits` (BigInt, ≤2 decimals) replaces `Math.round(Number(x)*100)`; rejects exponent/NaN/Infinity/negatives/commas/excess precision/unsafe integers. String amounts go through `minorFromString`.
- **Amount authority.** The **Agreement summary amount** (the Agreement summary read-model row) and "Evaluated for Payment Ready" (`money-status`, its own backend authority) are separate labelled sources. The summary row is *not* proven to be the current canonical version amount (Phase 6: an externally applied amendment can leave it behind), so it is never called "agreed" or "current". A same-currency difference is surfaced as: the two differ, SecurePay is using the evaluated amount for this readiness result, and this screen does not reconcile them.
- **State vocabulary.** Authorised maximum ≠ Funded ≠ Ready to progress ≠ Progressed ≠ Returned to funder(s). "Progressed within SecurePay" always (see below). Returning unused money is "not a settlement". History label FUNDED → "Funded". The list is "Money activity", not "Transactions".
- **`providerSettlementCertified` is not settlement proof.** Verified in SecurePayAPI: `AgreementFundedAuthorityOrchestrationService.established(...)` sets it from `choiceCertificationGate.isInternalTransferCertified()` — a certification/capability gate, not evidence that a specific progression was settled. The position card therefore always says "Progressed within SecurePay" and "SecurePay doesn't show a bank or provider settlement for this progressed amount here", for `true` and `false` alike; the boolean is not surfaced. A regression test covers `true`.
- **Release instructions: current vs earlier.** `instructions` is Agreement-wide history and each instruction is bound to an Agreement version. The panel is given the selected Agreement's `currentAgreementVersionId` and labels each instruction "Current Agreement version", "Earlier Agreement version" ("history, not the current release state") or, when the current version can't be established, neutral "Release history". Current release authority sits in its own block. No version UUIDs are displayed; older instructions still show their own settlement status.
- **Exact Agreement read (correction, review of `0800b91`).** An earlier pass refreshed the selected Agreement by searching page 1 of `GET /me/agreements` (paginated, default size 20), so an accessible Agreement off page 1 could be reported as "can't be found" and its version left unestablished. Selecting an Agreement now always re-reads it by id with `GET /agreements/{id}/detail` (`resolveSelection`): access is verified there and `currentVersion.versionId` is the one current-version authority for the handoff reconciliation, the release Current/Earlier classification and the selection itself. The paginated list remains only the picker/list source. If the exact read fails, nothing is claimed about access: Money shows "This Agreement's current context couldn't be refreshed…", release history is neutral and version labels are not shown. Test: an Agreement absent from a 20-item page-1 list still opens and establishes its version (the list is never consulted).
- **Settlement destination currency (correction).** The backend's `current` and `history` reads are currency-scoped (server default KES). The surface now has one explicit **Settlement currency** control (visible default KES, no transport default: the gateway methods require a currency) that drives current, history, register, replace and the post-success reload. Changing it clears current/history/verification and the form (the picker never shows KES facts beside a USD form) and loads only on "Show my <CCY> settlement destination". While an attempt is uncertain the currency is frozen with the rest of the request, and replace's two keys stay tied to that exact request. Logic lives in `settlementDestination.ts` (`readSettlementScope`, `submitDestination`) and is unit-tested with a recording gateway.
- **Handoff version race.** The in-memory handoff also carries the source `currentVersionId`. After Money re-reads the Agreement summary, the "version N" label is used only if it matches the fresh `currentAgreementVersionId`; otherwise the fresh title is shown with "The Agreement changed after you opened Money…" and the old label is dropped.
- **Settlement truth.** The backend phase `SETTLED` is emitted whenever an *execution record* exists (a dispatch outcome, sandbox-only) — the response carries no bank/provider proof — so the UI says "SecurePay recorded an execution…isn't shown as settled". Instruction ≠ reserved ≠ executed.
- **Bounded copy.** Payment Ready reasons, funding reasons, release reasons, intent statuses (PROVIDER_PENDING vs CONFIRMATION_PENDING distinct), money records and settlement phases each have a closed mapping; unknown → "can't describe yet". No raw provider metadata dump or redirect link exists anywhere in the Money layer (`PaymentIntentFunding.tsx` was deleted).
- **Partial failure.** Each panel reads independently; failure text is first-class ("Payment readiness couldn't be loaded", "Settlement status couldn't be confirmed", …), never zero/none/pending.
- **Session refresh.** `MONEY_AUTHENTICATED_METHODS` (typed table) drives every Money-family `withSessionRefresh`; a test parses each gateway source and fails if a method is missing/extra.
- **Settlement destination.** Hardcoded `currency: 'KES'` removed (explicit 3-letter input).
- **Hosted Money.** Confirm/redeem withheld with the limitation copy; the page still resolves and displays the session, shows no raw ids. The embeddable contract (origin-verified `postMessage` ready/cancelled) is unchanged; nothing was expanded.
